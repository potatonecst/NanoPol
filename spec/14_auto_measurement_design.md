# 仕様書: 自動測定アーキテクチャと制御仕様 (Auto Measurement Spec)

本ドキュメントは、ナノ粒子の偏光散乱光測定における「自動測定（Auto Mode）」を実現するための中核アーキテクチャ、制御フロー、およびデータ処理のポリシーを定義する。

## 1. アーキテクチャの基本方針（責務の分割）

自動測定では、「1つのサンプルに対して条件（ファイバの向き等）を変えて最大4回測定する」というワークフローが存在する。
システムの複雑化（God Objectの発生）を防ぐため、この管理を **Session Manager (UI層)** と **Measurement Manager (制御層)** の2階層に完全に分離する。

### 1.1 UI構成と用語の定義

ユーザー体験の直感性を高めるため、旧来の「State 0/A/B」という表現を廃止し、以下の3つのフェーズ（Phase）としてワークフローを定義する。

| フェーズ名 (UI表示) | 役割 | 識別子 (`autoPhase`) |
| :--- | :--- | :--- |
| **Session Management** | サンプルの新規作成、または過去の履歴（日付指定・Browse）からの再開 | `select_session` |
| **Category Selection** | 測定対象（Left-Front等）の選択と進捗確認 | `select_category` |
| **Measurement Execution** | 物理パラメータ入力、アライメント、および本番測定の実行 | `measuring` |

#### レイアウト構成 (`AutoView.tsx`)
`ManualView` の設計を踏襲しつつ、解析機能を強化したレイアウトを採用する。
*   **左側操作パネル (動的)**: 現在のフェーズに応じて操作UIを切り替える。`ManualView` と同様にレスポンシブ設計とし、画面幅縮小時は操作パネルを優先表示する。
*   **右側ビューパネル (固定/Resizable)**:
    *   **上段: CameraPanel**: 映像プレビュー、ROI操作、リアルタイム輝度（Sum/Max）表示。
    *   **下段: GraphPanel**: `recharts` を使用し、測定中の散乱強度プロファイルをリアルタイムにプロットする。
    *   **分割**: `shadcn/ui` の `ResizablePanelGroup` (垂直分割) を使用し、映像とグラフの比率を調整可能とする。

### 1.2 Session Manager (UI ＆ ワークフロー層)
*   **責務**: 「実験ノート」としての進行管理とユーザーへの指示。
*   **管理対象**:
    *   `outputDirectory` (ユーザー設定) の配下、`AutoMeasurementData/<日付>/<サンプル名>/settings.json` の読み書き（測定履歴の永続化）。
*   **セッション開始のロジック**:
    *   **日付選択 (Date Picker)**: `shadcn/ui` の `Popover` と `Calendar` を使用。今日以外の日付も選択可能とし、過去の実験データのスキャンに対応する。
    *   **新規作成の保存先固定 (Safety Rule)**: カレンダーでどの日付を選択していても、**`[New Sample]` による新規作成は必ず「実行した当日の日付フォルダ」に対して行われる**。過去の日付フォルダに新しいサンプルが書き込まれることは決してない。
    *   **自動採番のスキャン範囲**: 新規作成時の自動採番（Sample_N）も、常に **「今日の日付フォルダ」** をスキャンして重複しない最小の連番を決定する。
    *   **フォルダブラウズ (Browse)**: OS標準のフォルダ選択ダイアログを介して、任意の場所にある既存セッションをロード可能とする。
    *   **履歴表示 (Session Table)**: `shadcn/ui` の `Table` コンポーネントを使用。サンプル名、作成時刻、測定進捗 (例: 2/4) を一覧表示し、再開ボタン（Resume）でロード可能とする。
    *   **データのロード**: 過去の `settings.json` を指定することで、ROI設定や完了ステータスを引き継いで再開できる。
*   **測定の自由選択と非破壊的やり直し (Redo)**:
    *   4つの測定条件（例：Left-Front, Left-Rear, Right-Front, Right-Rear）は**順不同**で選択・実行可能とする。
    *   **非破壊ルール**: 一度実行した条件を再度選択して「やり直し」を求めた場合、過去のデータを上書き・削除してはならない。必ず新しいIDを発行し、履歴に追記すること。

*   **完了状態の判定 (UI表示)**:
    *   各カテゴリーの選択ボタンに、測定完了を示すステータスアイコンを表示する。
    *   そのカテゴリーの履歴の中に、`status: "completed"` となっているものが **1つでも含まれていれば完了** となす。
    *   履歴が `status: "aborted"` (飽和やユーザー中断による失敗) しかない場合は、完了状態とはみなさず再試行を促す。
*   **タイムスタンプの記録**:
    *   `settings.json` には、Measurement Manager が本番測定（Step & Shoot）を開始・終了した時刻を `timestamp_start` および `timestamp_end` として記録する。
*   **動作**: 次の測定の準備（Measurement Execution フェーズ）が整ったら、保存先ディレクトリを確定させ、設定値（ROI、角度リスト等）を添えて `Measurement Manager` に1回分の測定を委譲する。

### 1.3 Measurement Manager (ハードウェア制御層)
*   **責務**: 渡された条件と保存先パスに従い、**1回分の自動測定（Pre-Scan または Step & Shoot）をノーミスで完遂すること**。
*   **管理対象**:
    *   測定セッションの内部ステート（`Idle`, `PreScanning`, `Measuring`, `Paused`, `Finished`）。
    *   ステージ移動とカメラ撮影のミリ秒単位の同期制御。
    *   `DataSaver` を通じた CSV・画像・ROIメタデータの保存。
*   **独立性**: この層は「今がサンプルの何回目の測定か」を一切関知しない。与えられたタスクをこなし、結果（成功・失敗・飽和による中断）を上位に返すのみである。
*   **リアルタイムフィードバック (Graph)**:
    *   測定実行中、進捗イベント（Progress API）に含まれる最新の角度と輝度データを `recharts` で描画される `GraphPanel` に流し込み、リアルタイムでプロットを更新する。

## 2. データ処理と保存のポリシー（生データ主義）

定量的な物理測定の信頼性を担保するため、カメラから取得した画像データは、PCに到達した時点の**真のRAWデータ（無加工）**として保持・計算・保存する。

*   **スケーリングの禁止**:
    *   8-bitで受信したデータを、内部処理の都合で 16-bit（0-65535）に掛け算して引き伸ばすような処理は行わない。
*   **型の維持と保存**:
    *   カメラから `uint8` (8-bit) の Numpy 配列が渡された場合は、そのまま `uint8` として扱い、保存モジュールは 8-bit TIFF を生成する。
    *   将来 10-bit 等のカメラから `uint16` の配列が渡された場合は、そのまま 16-bit TIFF を生成する。
*   **ROI輝度計算**:
    *   計算（Sum, Max）は、データの型に関わらず生のピクセル値を単純加算（Sum）または最大値取得（Max）することで行う。
*   **リアルタイムフィードバック**:
    *   `CameraPanel` 表示中、バックグラウンドで ROI 内の `Sum/Max` を定期的に算出し UI に反映させることで、ユーザーによる手動での飽和確認を支援する。

## 3. Pre-Scan と オートセンタリングのアルゴリズム

Pre-Scan の目的は、波長板回転に伴う微小なプロファイル変動を考慮し、全角度で最も信頼できる「最適な1箇所」にROIを**固定（ロック）**することである。

### 3.1 実行手順 (Pre-Scan)
1.  **粗いスキャン**: ユーザーが手動で合わせたROIを初期値とし、ステージを粗い間隔（例：15度〜22.5度）で1周回し、複数枚の画像を撮影する。
    *   **証拠の保存**: 撮影した画像群（マルチページTIFF）と光強度データ（CSV）は、成否にかかわらず全て `prescan/attempt_X` として保存する。これにより、「なぜその試行が失敗したのか（飽和か、暗すぎたのか）」を後から完全に検証できる。
2.  **ドリフト防止の重心計算**: 各画像に対し、探索範囲を広げず**「設定されたROI枠内（＋数pxのマージン）」のみ**を対象に重心を算出する。
    *   **非反復（One-shot）計算**: 探索範囲を絞っているため、反復法による過剰なノイズ追従（微小振動）を避け、**1回のみの計算**で高速かつ確実に中心を決定する。これにより隣接粒子への「歩き出し（ドリフト）」を完全に防ぐ。
3.  **重み付き平均による確定**:
    *   **コントラストチェック（シグナル有無の判定）**: 全画像の中で最も明るかった「Max Sum」と、最も暗かった「Min Sum」を比較する。差が十分にない（例：`(Max - Min) / Max < 0.1`）場合は、偏光によるサインカーブが存在せず「ただのノイズ（平坦）」であるとみなし、全画像を却下して直ちに「アライメント失敗（NG）」とする。
    *   **ダイナミックな足切り（暗所の除外）**: 上記のコントラストチェックをパスした場合、「Max Sum」の一定割合（例: `Max Sum * 0.2` 等）を下回る暗い画像（消光位の谷）は、ノイズに引っ張られた不正確な座標になるため計算から除外する。
    *   **平均の算出**: 除外されずに生き残った有効な画像の「仮の中心座標」に対し、その画像の「Sum輝度」を重みとして**重み付き平均**を計算し、最も明るく信頼性の高い座標に収束させる。
4.  **ROIのロック**: 算出された最終座標にROIを完全に固定する。以降の本番測定（Step & Shoot）ではROIを一切動かさない。
5.  **履歴の記録**: 各試行の開始・終了時刻や成否は、枝番フォルダ内の `roi_settings.json` の `prescan_history` に配列として全て記録する。

### 3.2 Step & Shoot ループ (Measuring)
ロックされたROIを使用し、以下のループを実行する。
1. **Move**: 次の角度へステージを移動させる (`move_absolute` または `move_relative`)。
2. **Wait**: ステージの `is_busy` が `False` になるまで待機する。
3. **Shoot**: カメラで画像を1フレーム取得する。
4. **Process & Save**:
   - 取得した画像から固定ROIの Sum / Max を計算する。
   - `data.csv` に角度、時刻、ROI輝度、画像ファイルパスを追記する。
   - **画像保存**: ディスクI/Oによるコマ落ちを防ぐため、1枚ずつ別ファイルにするのではなく、**「マルチページTIFF」への追記（Append）** にて高速に保存する。
5. **Next**: 角度リストが終了するまで 1 に戻る。

## 4. 異常系のハンドリングとフェイルセーフ

### 4.1 飽和の動的判定
*   飽和とみなすピクセル値の閾値は、接続されているカメラの有効ビット深度（`camera.input_bpp`）に依存して動的に決定する（8-bitなら255、10-bitなら1023）。

### 4.2 アライメントと飽和の分離
*   **両方OK**: 測定開始ボタンが有効になる。
*   **自動開始トグル (Auto-start after Pre-Scan)**:
    *   利便性向上のため、Pre-Scan 完了後に自動で本番測定を開始するオプションを用意する。
    *   **カウントダウン**: 自動開始前に 3 秒間の猶予期間を設け、カウントダウン UI を表示する。この間、ユーザーは `[Cancel]` ボタンで自動開始を阻止できる。
    *   **リスク提示**: 15度間隔の Pre-Scan では「ステップ間のピーク角度」での飽和を検知できないリスクがある。このリスクは専門家であるユーザーの判断に委ねるものとし、トグルの近傍に警告を表示する。
    *   **判断材料の提供**: Pre-Scan 実行中、その時点での最大輝度（Max 255 等）を UI 上に大きく表示し、ユーザーがカウントダウン中に測定を強行するか中止するかを目視で判断できるようにする。
*   **飽和NG**: Pre-Scan のステップ中に実機限界（255等）に達した場合は、自動開始トグルが ON であっても強制的に停止し、ユーザーの確認を求める。
*   **飽和OK ＆ アライメントNG**:
    ノイズ等で重心計算が収束しなかったケース。特例として **強制開始（Force Start）** ボタンを表示する。ユーザーが手動でROIを合わせた後、このボタンを押すことで、システムは「飽和していないことだけを確認」し、重心のズレは自己責任として測定を強行できる。

## 5. UIコンポーネント設計（CameraPanelへの統合）

### 5.1 レイヤー構造の分離
カメラ映像のズーム（拡大・縮小）とUI要素の表示を両立させるため、DOMのレイヤーを以下のように分離する。
*   **画像＆ROI枠レイヤー**: `transform: scale()` などの影響を直接受けるレイヤー。カメラ映像（MJPEG）の上に、SVG 等で描画したROI枠を重ねる。これにより、画像をズームした際にROI枠も自動的に追従して拡大される。
*   **フローティング情報レイヤー（ミニテーブル）**: ズームの影響を受けない親コンテナ直下に絶対配置（`absolute`）するレイヤー。

### 5.2 ROIの基本操作と削除
*   **追加・移動・リサイズ**: カメラ映像上でのドラッグ操作により直感的に行う。
*   **削除操作**: 
    *   キーボード操作: `Alt + クリック`（Windows） / `Option + クリック`（Mac）で対象のROIを削除する。
    *   UI操作: フローティングパネル（ミニテーブル）内のゴミ箱アイコンクリックでも削除可能。

### 5.3 マウスイベントの競合回避
`CameraPanel` には「パン（平行移動）」機能が存在するため、これとROI操作が競合しないように厳密なイベント管理を行う。
*   ユーザーがROI枠を操作した際は、必ず `event.stopPropagation()` を呼び出し、親要素へのイベント伝播を停止する。
*   これにより、ROIを操作しようとして意図せず画像全体がパンしてしまうUXの低下を完全に防ぐ。

### 5.4 GraphPanel の統合
測定中のデータ視認性を確保するため、右側パネルを上下に分割して `GraphPanel` を配置する。
*   **配置**: `CameraPanel` の直下に配置。
*   **分割制御**: `shadcn/ui` の `ResizablePanel` により、ライブ映像とグラフの表示領域をユーザーが動的に変更可能とする。
